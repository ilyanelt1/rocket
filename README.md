# CheckStock — складской MVP

[Репозиторий CheckStock на GitHub](https://github.com/ilyanelt1/rocket)

CheckStock — отдельный прототип ядра остатков и движений для будущего проекта Raketa. Здесь реализованы складские остатки и операции; интеграции с WB API, прогнозирования, закупок и сезонности нет.

## Требования

- Python 3.14.2 для локальной разработки.
- Docker Desktop с Docker Compose для запуска приложения и отдельной интеграционной smoke-проверки.
- PostgreSQL 16 (поднимается через Docker Compose).

## Локальная установка

Windows PowerShell:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\Activate.ps1
python --version
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
pre-commit install
```

Проверь, что команда `python --version` выводит Python 3.14.2. Если установлен другой patch-релиз Python 3.14, установи именно 3.14.2 и повтори создание виртуального окружения.

## Настройка авторизации

Перед первым запуском создай `.env` на основе `.env.example` и обязательно замени секреты:

```powershell
Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Сгенерируй два разных значения: одно для `SESSION_SECRET`, второе для `ADMIN_PASSWORD`. Пароль администратора должен содержать не менее 12 символов. `ADMIN_USERNAME` задаёт логин первого администратора. Не добавляй `.env` в Git.

При первом запуске приложение создаёт администратора, если пользователь с `ADMIN_USERNAME` ещё не существует. Изменение `ADMIN_PASSWORD` после создания учётной записи не меняет сохранённый пароль. Дополнительных пользователей и роли создаёт администратор в разделе «Пользователи».

## Запуск через Docker

```bash
docker compose up --build
```

После старта приложение доступно по адресу http://localhost:8005. Страница входа: http://localhost:8005/login. Compose сначала дожидается готовности PostgreSQL 16, затем запускает одноразовый сервис `init`: он выполняет `alembic upgrade head`, после чего запускает воспроизводимый seed. Только после успешного завершения `init` запускается `web` с Uvicorn. Seed не перезаписывает уже существующие остатки и операции, поэтому повторный запуск не сбрасывает рабочие данные.

### Миграции базы данных

Схемой управляет Alembic. Новая пустая БД получает таблицы из baseline-миграции; существующие таблицы baseline не пересоздаёт (`checkfirst=True`). Следующая миграция добавляет `products.minimum_stock` только если столбца ещё нет, сохраняя существующие строки и значения. Все новые изменения схемы добавляй отдельными ревизиями Alembic, не изменяя уже применённые миграции.

Перед первым запуском новой версии на существующей БД обязательно создай и проверь резервную копию командами из раздела «Резервное копирование PostgreSQL». Миграции не удаляют volume, таблицы или данные; baseline намеренно не поддерживает разрушительный downgrade. В Docker Compose миграции выполняются одноразовым сервисом `init` до старта web.

Остановка: `docker compose down`. Для полного сброса БД вместе с volume: `docker compose down -v` (удалит все данные).

## Начальные данные

Seed создаёт товары и два ФФ — «Север» и «Юг»:

| SKU | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Seed выполняется одноразовым сервисом `init`. Повторно запустить инициализацию вручную можно командой `docker compose run --rm init`.

## Тесты и проверки качества

Unit-тесты используют SQLite in-memory для быстрого изолированного прогона бизнес-правил. SQLite не реализует PostgreSQL `SELECT FOR UPDATE`, поэтому эти тесты не подтверждают конкурентное поведение блокировок.

Отдельный `tests/test_postgres_integration.py` проверяет повторное и конкурентное подтверждение перемещения непосредственно на PostgreSQL. В CI для него поднимается отдельный PostgreSQL 16 service и передаётся `TEST_DATABASE_URL`. Локально этот набор можно запустить, указав `TEST_DATABASE_URL` на отдельную тестовую БД; тесты очищают и пересоздают таблицы в этой БД, поэтому не используй URL рабочей базы.

Запуск локально:

```powershell
pre-commit run --all-files
python -m compileall -q app tests scripts
python -m pytest -q
```

Docker Compose smoke test не запускается в pre-commit: он выполняется отдельным CI job, чтобы локальный коммит не требовал Docker и полной пересборки приложения. При необходимости локально запусти `python scripts/docker_smoke.py`. Скрипт использует отдельный Compose project `checkstock-precommit`, порт 18005 и отдельный volume; основной стек и его данные не затрагиваются.

Для проверки транзакций и блокировок требуется отдельный прогон на PostgreSQL 16 и отдельная тестовая база. Текущая фикстура unit-тестов намеренно создаёт SQLite engine независимо от `DATABASE_URL`; простая подмена переменной окружения не переключает эти тесты на PostgreSQL. PostgreSQL integration suite также проверяет конкурентное списание с одного ФФ и повторный запрос с одинаковым idempotency key.

## CI — GitHub Actions

GitHub Actions автоматически запускает проверки при push в `main`/`feature/**` и при создании pull request в `main`. CI использует Python 3.14.2 и разделён на два последовательных job:

- **Pre-commit, lint and unit tests:** `pre-commit run --all-files` проверяет форматирование и Ruff, YAML/TOML, пробелы, конфликты слияния, приватные ключи и размер новых файлов; затем `compileall` и `pytest`.
- **Docker Compose smoke test:** собирает образы, ждёт healthy-состояния PostgreSQL и web, запускает `scripts/smoke.py`.

Локально установи git hook командой `pre-commit install`. Перед коммитом выполняются быстрые проверки форматирования, Ruff и структуры файлов; полный прогон — `pre-commit run --all-files`. Docker smoke и PostgreSQL integration suite выполняются в CI.

## Что реализовано

- Товары с уникальным SKU и настраиваемым минимальным остатком, ФФ с архивированием, остатки по паре товар/склад.
- Остатки: физически, доступно, резерв FBS.
- Приход, перемещение между ФФ, FBS reserve/cancel/ship, FBO send/accept.
- История операций с поиском, фильтрами по товару/типу/статусу/складу/периоду и CSV-экспортом с учётом выбранных фильтров; три категории движения: между ФФ, FBO, к клиенту FBS.
- JSON endpoint сверки: `GET /api/reconcile/{product_id}`.
- Дашборд со сводными показателями по активным складам: физический остаток, резерв, доступное количество и товары без доступного остатка.
- Контроль минимального остатка: настраиваемый порог на товар, предупреждения при достижении или падении ниже порога; нулевой порог отключает предупреждение. Сравнивается суммарный доступный остаток на всех активных складах.
- Минимальный русский интерфейс на Jinja2, Bootstrap и HTMX; HTMX используется для AJAX-фильтрации и постраничной навигации истории операций.
- Авторизация с подписанной cookie-сессией и хешированием паролей PBKDF2-HMAC-SHA256.
- Роли `admin`, `warehouse_manager`, `operator`; права проверяются на сервере для каждого защищённого маршрута.
- Администратор создаёт пользователей, меняет их роли, блокирует и разблокирует учётные записи; учётная запись первого администратора создаётся из переменных окружения. Последнего активного администратора нельзя заблокировать или понизить в роли, а администратор не может изменить собственную учётную запись.
- Журнал аудита фиксирует успешные входы/выходы, управление пользователями и складами, а также складские операции; записи операций создаются в той же транзакции, что и изменение остатков.

## Ключевые решения и инварианты

1. **Доступно = физически − резерв.** Резерв не меняет физическое количество.
2. **Склад удаляется мягко.** Заполняется `deleted_at`; склад, остатки и история остаются в БД и видны в интерфейсе. Физическое удаление запрещено.
3. **Архивный ФФ нельзя использовать в новых движениях.** Его остатки остаются видимыми.
4. **Проверка локальная.** Операция проверяет доступный остаток на выбранном ФФ. Остаток другого ФФ не учитывается, автоматического перемещения нет.
5. **Изменения выполняются сервисным слоем.** Сервис фиксирует изменения и запись движения в одной транзакции; при исключении выполняется rollback. Для баланса и подтверждаемой операции используется `SELECT FOR UPDATE`.
6. **Идемпотентность.** У операции есть уникальный nullable `idempotency_key`. Повторный последовательный запрос с тем же ключом возвращает существующую операцию; переходы из активных статусов выполняются один раз.
7. **Движение в пути.** Перемещение и FBO отправка создают `IN_TRANSIT`; приёмка закрывает исходное движение. FBS отправка фиксируется статусом `SHIPPED`.
8. **Сверка.** Для SKU суммируются физические остатки на ФФ, движения в пути/к клиенту и принятые FBO количества. Приёмка перемещения не удваивает остаток: после неё количество учитывается на целевом ФФ.

## Интерфейс и сценарии

После входа открывается дашборд со сводкой по товарам, активным складам, физическому остатку, резервам и доступному количеству. Отдельно отображаются товары без доступного остатка и товары, достигшие минимального запаса. Минимальный остаток настраивается администратором или менеджером склада для каждого товара; значение 0 отключает предупреждение. Суммарное доступное количество сравнивается с порогом по всем активным складам, архивные склады не учитываются. Изменения порогов фиксируются в журнале аудита. Ниже расположены остатки по складам, склады (для администратора и менеджера) и операции. История открывается отдельной страницей `/history`: поиск по SKU/названию/примечанию, фильтры по товару, типу, статусу, складу и периоду, сортировка от новых к старым и пагинация по 50 записей. Фильтрация и переключение страниц выполняются через HTMX без полной перезагрузки страницы; обычный GET-запрос остаётся доступен как fallback. Кнопка «Экспорт CSV» выгружает все записи, соответствующие текущим фильтрам, в UTF-8 CSV с BOM для Excel. Фильтрация и подсчёт выполняются запросами к PostgreSQL; архивные склады остаются доступны в фильтре и отображении. Администратор дополнительно видит управление пользователями (смена роли, блокировка и разблокировка) и журнал аудита с последними 100 событиями. Для отмены/отправки FBS-резерва указывается ID исходного резерва из истории; для приёмки — ID операции в пути. Для повторяемого запроса можно указать idempotency key.

## Использование ИИ и проверка

ИИ использовался как помощник при проектировании структуры MVP, подготовке первоначальных вариантов моделей, сервисных операций, шаблона интерфейса, тест-кейсов и документации. Результат необходимо проверять запуском pytest, ручной проверкой всех пользовательских сценариев, анализом транзакционных границ и отдельным прогоном на PostgreSQL 16. Генерация кода ИИ сама по себе не является подтверждением корректности; особенно важно проверить конкурентные запросы и идемпотентность на PostgreSQL.

## Ограничения MVP

- Пока нет восстановления пароля, выгрузки журнала аудита и ограничения частоты попыток входа; для публичного production-развёртывания необходим HTTPS (`COOKIE_SECURE=true`) и reverse-proxy rate limiting.
- Нет WB API, интеграций маркетплейсов, прогнозов, закупок и сезонности.
- Нет отдельной сущности заказа FBS и доставки последней мили; отправка фиксируется движением.
- FBO-приёмка фиксирует остаток на стороне маркетплейса в движении, но не ведёт отдельный склад маркетплейса.
- Интерфейс минимальный; операции подтверждаются через ID из истории.
- Тесты по умолчанию быстрые SQLite unit-тесты; SQLite не проверяет блокировки `FOR UPDATE`. Перед сдачей рекомендуется прогон на PostgreSQL 16 и проверка конкурентных повторов.


## Эксплуатация: health checks, безопасность и резервные копии

### Health checks

- `GET /health/live` — liveness: подтверждает, что процесс приложения отвечает; не обращается к БД.
- `GET /health/ready` — readiness: выполняет `SELECT 1` в PostgreSQL и возвращает HTTP 503, если БД недоступна.
- Docker Compose использует readiness endpoint для проверки web-контейнера. PostgreSQL отдельно проверяется через `pg_isready`.

### Резервное копирование PostgreSQL

Резервная копия создаётся в формате PostgreSQL custom archive. Команды выполняются с хоста, где доступен Docker Compose:

```powershell
python scripts/db_backup.py backup
python scripts/db_backup.py verify backups/<имя-файла>.dump
```

- `backup` создаёт файл в `backups/` с UTC-временем в имени.
- `verify` поднимает временную БД внутри контейнера PostgreSQL, восстанавливает архив в неё и проверяет наличие таблицы `products`. Временная БД удаляется после проверки.
- Восстановление в рабочую БД — разрушительная операция. Останови приложение и выполни `python scripts/db_backup.py restore backups/<имя-файла>.dump --yes`. Скрипт сам создаст дополнительную страховочную копию текущей БД в `backups/pre_restore_*.dump` до начала восстановления. После восстановления запусти приложение и проверь данные.
- Скрипт использует параметры подключения из `.env`/окружения: `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`. Пароль рекомендуется генерировать в URL-safe формате, например `secrets.token_urlsafe(32)`.
- Файлы резервных копий не должны попадать в Git или храниться только на том же диске, что и база. Для реального production настрой регулярное копирование на отдельное защищённое хранилище и политику хранения (например, ежедневные копии + ротация).

Пример ежедневного запуска на Windows — через Task Scheduler; на Linux — через cron/systemd timer. Перед использованием расписания сначала проверь ручной backup и restore на тестовой БД. Резервная копия считается проверенной только после успешного тестового восстановления.

### Безопасность перед публикацией

- В production установи уникальные `SESSION_SECRET`, `ADMIN_PASSWORD` и `POSTGRES_PASSWORD`; не используй значения из примера.
- Разворачивай приложение за HTTPS reverse proxy и установи `COOKIE_SECURE=true`. При HTTP локальной разработки оставляй `false`.
- PostgreSQL публикуется только на loopback-интерфейсе хоста: по умолчанию `127.0.0.1:5433 → 5432`. Он не доступен с других устройств сети. Для изменения локального порта задай `POSTGRES_HOST_PORT`; не привязывай БД к `0.0.0.0` в production.
- Security middleware добавляет `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и ограничивающий `Permissions-Policy`.
- Ограничь доступ к резервным копиям и секретам на уровне ОС/хранилища. Не передавай архивы через публичные ссылки.
- Перед открытием сервиса в интернет добавь HTTPS termination, rate limiting на reverse proxy, централизованный сбор логов, мониторинг свободного места и оповещения о неуспешном backup.

### Локальная проверка готовности

```powershell
docker compose up --build -d --wait
Invoke-RestMethod http://localhost:8005/health/live
Invoke-RestMethod http://localhost:8005/health/ready
python scripts/db_backup.py backup
python scripts/db_backup.py verify <путь-к-архиву>
docker compose down
```


## Дополнительные эксплуатационные решения

- cancel_fbs и ship_fbs могут завершить уже созданный FBS-резерв, даже если исходный склад позднее архивирован. Это позволяет закрыть существующее обязательство и не оставлять резерв навсегда; архивный склад по-прежнему нельзя выбирать для новых операций.
- Все изменяющие состояние действия доступны только через POST; cookie-сессия использует SameSite=Lax. Перед переходом на SameSite=None или добавлением GET-мутаторов необходимо внедрить CSRF-токены.
- При публикации за HTTPS reverse proxy настрой HSTS и Content-Security-Policy на уровне proxy после проверки доменов и источников ресурсов интерфейса. Сейчас приложение не отправляет эти заголовки автоматически.
- SESSION_SECRET обязателен при прямом запуске приложения и должен быть стабильным между перезапусками и всеми workers; допустимая длина — не менее 32 символов.
- PostgreSQL image использует major tag postgres:16, чтобы получать актуальные minor/security updates ветки 16. Для воспроизводимых production-развёртываний рекомендуется фиксировать проверенный patch tag или digest и обновлять его контролируемо.


При запуске db_backup.py verify с ролью без CREATEDB выполняется проверка структуры архива без создания БД; для полного тестового восстановления используй отдельную роль с CREATEDB.
